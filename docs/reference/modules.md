# Module catalog

The parts of the product under `backend/internal/modules/`, each with clear limits. Use this page to find
the module a change belongs to, or to place a new one. The page is written by hand, so `internal/modules/`
has the last word on which modules exist. A folder this catalog does not list yet is still a module. For
*why* modules have these limits (the DAG, the two spine shapes), see
[explanation/architecture.md](../explanation/architecture.md). For the store and write rules every module
shares, see [explanation/write-backbone.md](../explanation/write-backbone.md).

## Module shape

A module is flat by default: store, contract mapping, HTTP handlers and provider part in one package. It
gets its own package in the module only for an adapter to an outside system, or for an engine that
is separate. Rules kept from the rest of the module also get one. Some modules are a seam (a register, a factory) and not an HTTP feature; the
Spine column says so.

The `Owns tables` column links to the module's page in the [table list](entity-model/README.md). That
page is generated from the schema and from `tableOwners` in `backend/gates/tableownerregistry_test.go`, so it
is the one list of which module owns which table. `backend/gates/tableownership_test.go` checks the writes
in the code against that map. The few approved writes across stores (merge links, GDPR erase) are
`crossStoreWrites` in `backend/gates/tableownershipwaivers_test.go`. The import, owner and spine rules are in
[architecture.md](../explanation/architecture.md); the gates that hold them are listed in
[`backend-onboarding.md` → gates](../explanation/backend-onboarding.md#the-gates-that-judge-your-pr-fitness-functions).

Some tables are owned by the `compose` layer or by `platform`, and not by a module. Their pages are
[compose.md](entity-model/compose.md) and [platform.md](entity-model/platform.md). A `compose` table that
holds view state for one reader, or a stored result worked out from other rows, is written with no audit
row. A row made for one reader is never served to another, so an audit log over it would record reading,
not change.

Features at the `compose` level are not modules either: they wire module stores together
([explanation/composition-layer.md](../explanation/composition-layer.md)). These are company context, the HTTP
part for a cold start, reply drafts, running a deep read, and the AI model test lane.

## Packages in modules

- `identity/internal/policy`: the role permission policy documents (kept from the rest of the module).
- `identity/internal/password`: `Argon2id` hash and check.
- `agents/runner`: the Surface-B loop that reasons, acts and looks at the result (its own `Store`, catalog, window).
- `capture/{imap,gmail,graph}`: the mail capture connector for each provider.
- `capture/{gcal,graphcal}`: the calendar connector for each vendor.
- `capture/oauthflow`: the shared OAuth connect and callback flow.
- `capture/mailmap`: email and domain mapping.
- `capture/meetingmap`: the calendar rules both calendar connectors use.

## Where links between modules are wired

A module never reaches another module; the `compose` root injects the link (how that works:
[explanation/composition-layer.md](../explanation/composition-layer.md)). The current links (wired in
`internal/compose/server.go`):

- **deals ← projects**: whether a project may be attached to a deal. Also moving the project of a `won`
  deal into delivery. Both happen in the same transaction as the deal write
  (`deals/projectseam.go`, wired in `compose/installseam`).
- **the workspace seed in identity** ← deals (default pipeline) + consent (default purposes and
  retention) + automation (starter automations) + activities (booking page), in one bootstrap
  transaction.
- **staged calls in agents** (staging and use) ← approvals (adapter).
- **the approval queue in agents** ← approvals (a second adapter: the tools that list, read and answer
  what is waiting).
- **the action seams in automation** ← collections (add to list); activities + consent (draft an email +
  the outbound suppression gate); approvals (🟡 staging). Also activities (the scan for no activity and
  for a check-in), and identity (the owner permission check again at match time, through
  `authz.Resolver`).
- **DSR erase in consent** ← the `Eraser` of privacy.
- **relationship strength in signals** ← the store of contacts (adapter).
- **the outbound gate in activities** ← consent (the suppression gate) + the public seams of contacts
  and consent.
- **owner scope on webhook delivery** ← identity (the check again, when the delivery is queued, that
  the owner may see the event, through `authz.Resolver`).
- **imap connect** ← the connector register of capture (adapter).
- **filtered export** ← the saved view or list source of collections (adapter).

To place a new module, follow [add-a-module.md](../how-to/add-a-module.md).

## Background tasks

`platform/datatask` owns `data_task_run`, the saved place of each data task between runs.
It receives step functions from compose and never imports a module. Capture owns provider-date
stamping, contacts owns source provenance, and consent owns privacy-notice changes. Their
transaction functions share the same transaction. See
[Background data tasks](../explanation/data-tasks.md).

# The jobs of the merge gate

What each job of [`ci.yml`](../../.github/workflows/ci.yml) checks, with the jobs of its lanes
([`_lane-integration.yml`](../../.github/workflows/_lane-integration.yml),
[`_lane-frontend.yml`](../../.github/workflows/_lane-frontend.yml)); those files declare the jobs. Which jobs a change reaches, and why the gate is shaped this way:
[ci-pipeline.md](../explanation/ci-pipeline.md). The workflows outside the gate:
[ci-workflows.md](ci-workflows.md).

| Job | What it checks |
|---|---|
| `changes` | The [scope classifier](../explanation/ci-pipeline.md#run-only-the-checks-a-change-can-reach) (it always runs first, when not a draft; its answer is overridden on `merge_group`) |
| `ci-image` | Names the [CI image](../explanation/ci-image.md) for this tree by digest. A run that may push builds and pushes a missing image first. An empty name, on a fork or while the package needs a login, runs the jobs on the runner. It is in the `ci` aggregate, so a broken image build fails `ci` |
| `deterministic-gates` | Three legs of `make check-backend`, each passing its share as `CHECK_LEGS`: `unit` runs `test-cached test-extensions`, `gates` runs `test-uncached`, the root fitness packages that were most of the test time, and `solo` runs `test-solo`, the `SOLO_TEST_PKGS` whose time beside the rest was the load on the runner. Each runs build and their share of the tests (with `audit_log` enum agreement + the contract `$ref` check before the run). Only `unit` runs generated drift, `check-composition` and the script gates: `gates` and `solo` pass `CHECK_TREE_GATES=off`, and `TestOneBackendLegRunsTheTreeGates` fails if every leg does. The script gates are the craft doc floor, image pins, contract breaking, test lanes, file length, `rls-store-path`, jurisdiction isolation, and the lock on the published `backend/pkg` surface. Outside a PR into `develop`, the `unit` and `solo` legs each run their tests uncached through `scripts/testlog-exec.sh` and then `make test-input-census-judge`, so a test that reads a file outside its module without reading that file's tree digest fails the PR that adds it. After the merge gate, the `unit` leg copies in the `crm-hello` fixture and runs `build`, `check-composition`, the `cmd/` tests and every unit's own tests over it, then uploads their coverage profile for `sonarcloud`. Each leg then uploads its test log for `test-budget`. It checks out every commit with `filter: blob:none`, and git fetches an older file when a gate reads it |
| `test-budget` | [`make test-budget`](make-targets.md#root-script-gates) takes one or more logs, and this job passes every `deterministic-gates` leg's log: a unit-test package over 120 seconds fails, unless `scripts/test-budget-waivers.txt` gives it a higher ceiling. A waiver for a package neither leg ran is stale and fails too |
| `backend-lint` | `make check-static`: vet, lint (baseline + strict for new code) and `arch-lint`, the legs `deterministic-gates` leaves out. Two legs, each passing its share as `STATIC_LEGS`: `baseline` runs `lint-base`, `vet` and `arch-lint`, and `strict` runs `lint-strict` and `lint-modules`. The baseline pass loads the whole tree, so it gets its own runner. The strict pass loads only the packages that hold a changed `.go` file, which leaves room for the modules outside `backend/`. Both load the `lint` Go build cache that `lint-cache.yml` saves on `main`, and run under the `backend_lint` scope, which leaves out `frontend/**` and `docs/**`. `TestTheTwoBackendJobsRunEveryCheckLeg` fails when the two jobs stop covering every leg of a local `make check`. Only the `strict` leg checks out history, with `filter: blob:none`. |
| `craftsmanship` | `make craft-static`, strict: BLOCKER **and** MAJOR findings fail it, and MINOR is advisory. Then `make comment-stats`, which fails when the tree's comment numbers go up. It starts beside `deterministic-gates`, not after it |
| `craft-residue` | No open `CRAFT-FIX`/`CRAFT-DISPUTE` markers reach `main` |
| `secret-scan` | gitleaks over the committed tree, then the scan's own tests and the image pin gate; see [What `secret-scan` runs](../explanation/ci-pipeline.md#what-secret-scan-runs) |
| `integration build` | `make test-integration` with `INTEGRATION_BUILD_OUT=dir`: one `go test` compiles and links the test binary of every integration package, with the tag and coverage flags the shards use, and the binaries go up as one packed file. `zstd --long=30` packs it, because its 1 GB window finds the code the binaries share, and the shards need the same window to open it (`LANE_BIN_ZSTD`). The pack also holds the test times the shards split by: the newest `integration-test-timing-*` cache entry, or the committed `scripts/integration-test-timing.txt` when there is none. It also holds how the shards share the lane: `scripts/shard-queue-mode.sh` makes one claim in the cache service, and the answer is `queue`, or `fixed` when the run may not write caches. It needs no database. It uploads the pack as `test-binaries-integration-<attempt>`. When it fails or is cancelled it uploads `test-binaries-integration-<attempt>-failed` instead, and the waiting shards stop |
| `integration shard (k/8)` | `make test-integration` with `INTEGRATION_SHARD=k/8` and `INTEGRATION_QUEUE`: the shards share one queue of the lane's parts. Each part is one process of about 120 seconds of tests, cut by the file of test times `integration build` packs with the binaries (`INTEGRATION_TEST_TIMING`). The parts make groups of about 240 seconds, slowest first. When a slot is free, the shard claims a group in the cache service (`scripts/lib-shardqueue.sh`), so a fast runner runs more groups than a slow one. Old times make the end less even, but never drop a test. When the build gives `fixed`, the shard runs a fixed part instead, handed out slowest first. After `Re-run failed jobs`, a shard skips the groups that green shards of the earlier attempt ran. It runs with `INTEGRATION_JOBS=8`. It starts beside `integration build`, with no `needs`. While the build compiles, it boots the dev compose stack (`make db-up`: Postgres 16 (pgvector) pinned by digest + Redis 7 + MinIO + the app role; one stack file, and no GH services mirrored by hand) and builds its own `margince_test` template with migrations run (`make test-db-up`). It then waits for the binaries of its attempt (`scripts/wait-lane-binaries.sh`). It polls the run's artifact list in the results service, which costs no REST call. It asks the REST API only what that list cannot answer: a re-run asks at once whether its attempt builds again, a first attempt asks after 6 minutes with no artifact whether the build ended, and both ask again every 3 minutes while they wait. It copies the template per package. With `INTEGRATION_BIN_DIR` it runs each package from the binary of `integration build`, in the package directory, so it compiles no test code. It fails before any test runs when a binary for one of its packages is missing. It uploads the manifest of its part, the groups it claimed, the run time of each of its tests, and each binary coverage pod |
| `integration unit coverage` | The unit `-cover` pass over every package that has code of its own (a test-only package such as `backend/gates` is skipped), with a binary coverage pod only. No services (the test lanes gate checks that tests with no tag open no real DB) |
| `integration` | The fan-in that the `ci` aggregate reads, standing for the whole sharded lane. It checks that the build and the unit pass passed; a failed job turns it red, not skipped. Then `scripts/test-integration-reconcile.sh` proves the parts add up: every shard is there, they found the same tests and split by the same test times, and together they cover all with no overlap. A red or lost shard is named, with the groups it claimed and the tests no green shard ran. Only then does it check that every shard passed. It also fails on an entry in `backend/tools/sql-census/repeated-gates.txt` that no shard saw repeat the content gate, so that list only shrinks. It merges every coverage pod into `coverage.out`, and uploads `go-coverage`, and every shard's test times as `test-timing-integration` |
| `integration (extension migration gate)` | `make check-ext-migrations`, beside the shards rather than after them, because it reads the tree and no shard output. The dev compose stack starts only when an enabled unit declares `migrations/`. Being in the same lane as the shards, its result reaches the `ci` aggregate too |
| `images (build only)` | `docker buildx bake` of the default group (the three roles), pushing nothing; runs on the `images` scope |
| `vuln` | `make vuln` (govulncheck over all packages). **Advisory**: it sits outside the `ci` aggregate, so a red one does not stop a merge. It runs on every backend change, and `scheduled.yml` runs it daily on `main` |
| `license gate` | `make test-sbom-census`, then `make sbom-gate`: `make sbom`, then `make sbom-check`, both run again when grant refuses a package, up to three runs. It holds the license policy for dependencies (`grant`, policy in `.grant.yaml`), over the resolved dependency graph, not each manifest. It is gated at the job level, so a path skip reports as passing. It runs on `merge_group` as well as `pull_request`. It is the **only** run of this policy that starts on its own; `sbom.yml` runs only by hand |
| `fe-quality` | `make fe-quality`: the design system script gates, the check for contract type drift, Biome, the type check of the composed SPA, and the vitest suite of each unit screen. It is the only frontend job with a Go toolchain. It loads the type check and compiler lint caches that `cache-warm.yml` saves on `main` |
| `fe-unit (k/4)` | `make fe-unit FE_COVERAGE=1 FE_SHARD=k/4`: one of four parts of the vitest suite, split by the expected cost of each file (`frontend/scripts/vitest-shards.ts`) rather than by a hash of its path. The test files that load the TypeScript compiler run as their own vitest project, `source-scan`, without isolation, so a worker loads the compiler once. The two that type-check the whole tree run that check in a worker thread, where the coverage count does not slow the compiler. The run that decides the verdict also holds the coverage. It uploads a **blob** report, not an lcov |
| `frontend` (merge half) | `make fe-unit-merge` in the fan-in: `vitest --merge-reports` adds the four blob reports into one verdict and one lcov. `frontend/scripts/check-shard-union.sh` then proves the parts split the suite with nothing left out (every file found was run, once). `check-lcov-paths.sh` proves every path in the report resolves from the repo root (see [Coverage → SonarCloud](../explanation/ci-pipeline.md#coverage--sonarcloud)). It writes `fe-coverage` |
| `fe-bundle` | `make fe-bundle`: the Vite production build plus the Storybook catalog build (stories must compile and register). It loads the same cache as `fe-quality` |
| `frontend` | The fan-in that the `ci` aggregate reads, standing for every SPA job. It checks that all of them passed; a failed lane turns it **red, not skipped**. That check runs first, before the merge half above. The SPA jobs run at the same time |
| `uat` | `make frontend-e2e`, split over three jobs with `playwright test --shard`: the `AC-<screen>-N` screen tests that set what is accepted, as named Playwright tests + axe WCAG 2.2 AA + the sweep that checks no page moves side to side at `390px` + the PERF-1 claim that a record opens with the read held. It reads no clock. It fakes the API at its edge, so it needs nothing outside itself |
| `live-boot` | The README steps to start, run as written: compose up → migrate → api → `seed-dev` → `verify-boot`. It covers the seed that runs through the API, and the boot proof. It leaves the frontend build to `fe-bundle` (`VERIFY_BOOT_FRONTEND_BUILT_BY`), which runs each time an input of that build changes |
| `home-budget` | `make home-budget`, on an api booted as `live-boot` boots it: the `p95` of Home's reads, cold and warm (cold: uncached, on a new app whose connections served Home until Postgres had to choose each statement's plan; the first reads after a new release or a restart are not measured), then how fast Home's day list shows, and CLS, on a production build. On a pull request its first step (`scripts/home-budget-scope.sh`) skips the rest unless the diff holds a Go file or migration under `backend/`, a dependency Home shares, a file of the check, or a frontend file that Home's first load or the browser check imports (`frontend/scripts/home-reach.ts`). It measures the base commit on the same runner too (a pull request's merge base, the commit before a push, a merge group's base) and fails only when the change is slower than the base past a margin, so runner speed cannot turn it red; a new branch with no base is judged on the fixed budgets. The job summary holds the comparison, each half's wall time, every API row and the `day_paint_p95_ms` and CLS line. Not in the `ci` fan-in |
| `sonarcloud` | The scan run from CI ([Coverage → SonarCloud](../explanation/ci-pipeline.md#coverage--sonarcloud)). It waits for the jobs that make coverage, not for `ci`, and does not run on `merge_group` |

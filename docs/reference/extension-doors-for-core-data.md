# How extensions reach core data

An extension is a separate unit under `extensions/` that adds to Margince. These are the ways an
extension adds core records, reads them, and learns when they change. Each row names the page with the details.

## What an extension can do

| Feature | What an extension can do | Details |
|---|---|---|
| Outside-id storage and lookup | Keep the id a contact, company, deal or project has in another system. Find a company or deal by it. | [rest-api.md](rest-api.md#an-id-from-your-system) |
| Service member for timed jobs | Make an account that nobody signs in as, keep the secret of a timed job under it, and add records as it. A user who leaves does not stop the job. | [declare-a-service-member.md](../how-to/declare-a-service-member.md) |
| Intake path for deals and companies | Send a company or a deal with the id it has in the system it came from. A company typed by hand is matched by its domain. A deal can change stage, and activities can be moved onto the record. | [land-companies-and-deals-from-an-extension.md](../how-to/land-companies-and-deals-from-an-extension.md) |
| Reads of core records | Read deals, companies, signals, activities and the custom-field list as the caller who made the call. Filter by custom-field value and by the outside id. Each list is audited as an export. | [read-core-records-from-an-extension.md](../how-to/read-core-records-from-an-extension.md) |
| Erase and merge events | Listen for `company.erased`, `deal.erased` and `deal.merged`. Each carries ids only. The shape of a read of an erased id, id and kind only, is declared as `Tombstone`; no read returns it. | [react-to-record-lifecycle-events.md](../how-to/react-to-record-lifecycle-events.md) |
| Notices | Send a notice about a contact, company or deal to a member or a role. The extension names no address. The core finds live members who can open the record and picks the channel. The notice holds a link, not a copy of the record. Capped per extension. A notice started by a scheduled job is refused. | [send-a-notice-from-an-extension.md](../how-to/send-a-notice-from-an-extension.md) |
| Skip fields a user edited | An extension that updates a company or deal leaves alone a field a user last edited, and the result names the fields it left alone. A deal's amount and currency are always left alone together. An admin can let one extension overwrite them instead, under Settings, Extensions, or with `PUT /v1/extensions/{name}/settings`. The setting is off by default and each change is audited. | [land-companies-and-deals-from-an-extension.md](../how-to/land-companies-and-deals-from-an-extension.md) |
| Keep the outside value beside the typed one | The core keeps the last value each extension offered for a company's `legal_name`, `industry` and `description`, even when a user's edit kept the record's own value. `GET /v1/companies/{id}/offered-values` reads them, for a signed-in user who may read the company. Erasing a contact deletes the offered values of the companies they worked for. Deals are not covered, and the record page does not show the values. | [land-companies-and-deals-from-an-extension.md](../how-to/land-companies-and-deals-from-an-extension.md#see-what-a-unit-offered) |
| Large load that can resume | Hand over up to 200 records of one source in a batch, with a place the core saves once every record is answered. A restarted job reads the place and carries on. A record that the core refuses with an error ends the batch and leaves the place where it was, so a record that always fails stops the load until the unit drops it. A record the core skips or cannot store as given does not end the batch. Only an unattended run may load a batch. | [land-companies-and-deals-from-an-extension.md](../how-to/land-companies-and-deals-from-an-extension.md#load-a-large-source-in-batches) |
| Extra notes on core records | Add a small fixed note to a contact, company or deal page. It shows only to a reader who may read the extension's data, and it carries no record data. | [add-an-extension.md](../how-to/add-an-extension.md#offer-an-entry-on-a-core-screen) |
| Per-extension settings page | Declare settings as data, a switch or one line of text. The core shows them on the unit's card under Settings, Extensions, to admins only, lets only an admin change them and audits each change. The unit's own code does not read them. | [add-an-extension.md](../how-to/add-an-extension.md#declare-settings-an-admin-can-change) |
| SQL on the unit's own tables only | An extension's `Tx` runs each statement as the `ext_runtime` database role, which holds only schema `ext`. The database refuses a core table, `extension_secret` included, with `ErrCoreTableRefused`, even when the table name is built at run time. The role guards against errors by trusted first-party units, not against unit code that means harm: one statement can switch back to the login role. Another unit's `ext` tables are not refused by the database. The static check `extensionsqlscope_test.go` refuses both in the source. A separate login for each unit ([issue 628](https://github.com/margince/margince/issues/628)) would make the limit hold against such code. | [add-an-extension.md](../how-to/add-an-extension.md) |

The reasons behind the outside id are in [outside-ids.md](../explanation/outside-ids.md).
